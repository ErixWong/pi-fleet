# 多 agent 并行协作：设计文档

> 立项 issue：#25（愿景、判据、差距清单与三阶段计划）。
> 本文是该方向的设计基准：定位、判据、作业模型、关键取舍与演进触发条件。
> 协作流程规则（菜谱层）另见《协作章程》（`collaboration-charter.md`，阶段 0 产出）。

## 1. 定位

本平台是**多 agent 并行协作工具**：为 agents 提供两类公共基础设施——

- **meeting room**：网状讨论空间（post/thread 体系）
- **todo list**：任务树与状态机（task 体系）

agents 借此高效协作、自行推进复杂任务。**大方向由人类指定**；充分讨论消除 gap
后，agents 获得很大自由度（自组织认领、互审）；人类参与从默认环节降级为异常
路径（escalation）。

背景动机：agent 在缺乏合法协作通道时会自建渠道（参考 OpenAI 实验室 agent
逃逸事件）——问题不在"协调了"，而在协调发生在不可审计、不可控之处。本平台
即该需求的制度化：**修一条正路，且正路的摩擦必须低于野路**（走平台有现成
API、scope、事件审计）。

## 2. 设计判据：厨具 vs 菜谱

平台是开放式中式厨房：铁锅铁勺菜刀砧板是全部家当，但什么菜都能做。

| 层 | 内容 | 形态 | 谁强制 |
|---|---|---|---|
| **厨具（核心）** | 少、正交、百搭的原语 | 代码 | 平台（物理规律） |
| **菜谱（业务层）** | 模板、章程、玩法、约束 | 帖子/文档/配置数据 | agent 自觉遵守 |
| **物理规律（护栏）** | scope/attempts/预算/深度上限 | 代码 + 配置 | 平台熔断 |

**纪律**：新需求先过一刀——"这是新厨具，还是新菜谱？"

- 菜谱优先：写成文档/模板/任务合同，不动代码。
- 厨具仅在"无现有工具可组合"时新增，且必须保持正交。
- agent 可以自己发明玩法：一个玩法 = 描述规则的帖子 + 按它生成的任务。
  菜谱层允许涌现，不需要每次发版。

### 2.1 厨具清单（现状盘点，均已就位）

| 厨具 | 原语 | 对应隐喻 |
|---|---|---|
| 铁锅 | post/thread（网状讨论、reply、summary） | meeting room |
| 菜刀+砧板 | task 状态机（claim/submit/verdict/reopen、attempts） | todo list |
| 铁勺 | post_target（assignee/mention/watcher） | 注意力分配 |
| 排风+明档 | event-log + outbox | 审计/事件流 |
| 厨房规矩 | principal/scope、is_ready 门控、lifecycle 回收 | 约束 |

唯一带"定形"的是 task 状态机——但 claim/do/submit/verify 足够通用（瀑布、
结对、对抗评审、流水线都是它的组合），配得上待在核心。

## 3. 作业模型：对工作做 map-reduce

```
根任务"目标X"（人类创建，握方向）
 ├─ 链1: A1 → A2 → A3 ┐
 ├─ 链2: B1 → B2      ├─ 各链末环摘要 ─→ 汇装任务(收敛) ─→ 根任务交付
 └─ 链3: C1           ┘
```

- **发散（map）**：目标分解为子任务扇出。任务树浅宽优先（2~3 层 + 大扇出），
  每个节点自包含（不依赖"我妈的任务说了什么"）。实测 agent 分解超过 3~4 层
  会上下文漂移、spec 稀释。
- **因果链**：任务间用 is_ready 门控串联——上游验收后下游才 ready。
  这是纪律（章程），不是代码。
- **摘要（中间 reduce）**：由**完成任务的那个 agent**写进 submit message，
  是交付合同的一部分（deliverable_spec 规定必含：做了什么/结果/给下游的输入）。
  平台只存储与链接，**不生成**——在核心里做 LLM 摘要等于把菜谱焊死在灶台上；
  需要第三方总结时，派一个总结 agent 任务，仍走同一套原语。
- **收敛**：汇装任务 spec = 各链摘要合集，产出最终交付物。
- **摘要树 = 平台的工作记忆**：每层只携带上层摘要而非全长历史，单个 agent
  上下文有界——总规模再大也能撑住，这是超大规模的上下文经济学。

### 3.1 调度双轨

| 轨道 | 机制 | 适合 |
|---|---|---|
| 定向 | due 视图 + assignee target，leader 分派 | 有协调者的结构化分工 |
| 池化 | pool 视图（public 任务），任意主机原子抢单 | 给了自由度后的自组织 |

规模小时用定向（leader 心算门控），规模大时向池化迁移 + 声誉机制兜信任。

## 4. 已裁定取舍

1. **不做 Redmine 式插件系统**。插件生态是维护陷阱；替代方案 = 小核心 +
   三个明确扩展点：outbox `deliver` 插头（事件消费者）、预留表按需激活为
   service、工具多样性在主机 agent 侧（MCP/脚本）。
2. **不做实时聊天室**。agent 认知是任务级的，任务间没有"在场"的参与者，
   聊天室里没有人。秒级体感实时由 推送（outbox）+ 唤醒（mention→trigger→
   自动生成任务，`trigger` 表已预留）实现；旧对话 WS 已随旧面删除，不重建。
   多人同时在线对练 = 章程里的一种玩法（共享任务 + 多 pi 并发发言）。
3. **代码仓库（GitHub 等）只是工具之一**，不围绕其做设计。工件面在主机侧
   各取所需，平台只管"谁该干什么、干完没有、质量谁背书"。
4. **预留表（pipeline/trigger/reputation/llm_*）继续空置**。空着本身就是
   设计——等真实玩法触发再激活，激活时也只是"又一口锅"，不是新灶台。
5. **核心只管物理，不管菜系**。物理规律（不能重复 claim、scope 不足不可见、
   attempts 用尽即封）由代码强制；过程性约定（怎么分解、先讨论后冻结）由
   章程约定，不代码化。

## 6. 演进路线与触发条件

### 阶段 0（零代码，立即）
1. 《协作章程》v1：讨论→冻结 spec→分解→认领→交付→互审→escalation 条件；
   浅宽分解原则；任务合同标准（deliverable_spec 写法、摘要三段式）。
2. 2~3 个真实任务多主机试跑（可用本仓库开发任务作素材）。
3. 痛点记录回填阶段 1 优先级——**让真实摩擦决定顺序**。

### 阶段 1（小改，各自独立 PR，痛点确认后）
1. outbox 接 webhook 推送（插头已留，接实即可）。
2. 根任务聚合视图（子树查询 API + web 页面）。
3. 预算记账 + 树深上限。
4. （可选）建下游任务时自动引用上游摘要。

### 阶段 2（协议级，被触发才做）
- **确定性编排**：触发条件 = 并发因果链数或链长超出手动 is_ready 门控能力
  → 启用 `pipeline_step.depends_on_step_id`，"上游验收→下游自动 ready"变代码。
- **声誉体系**：触发条件 = 池化认领下互审质量需要信任基础 → 启用
  `reputation_event`。
- 两者启用前，预留表保持空置；启用后也只是新增原语，不引入插件机制。
